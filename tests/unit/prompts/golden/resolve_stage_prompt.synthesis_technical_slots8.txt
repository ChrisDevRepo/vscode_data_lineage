**Mission type:** technical

### Output templates (synthesis)

- summary: One-line graph purpose — aim for ~120 chars. Shown in the info card. This is prose, not a fixed-width label: write the full purpose; avoid padding or clipping to a number.

- title: Optional. Aim for ≤80 chars (hard cap 120 — over-length titles are rejected and re-asked). Names the analysis subject and its key finding: "[Subject] — [key computation, pattern, or finding]". Include the final output object if space allows. Omit step counts and numbers. GOOD: "NetAmountA — QtyA × PriceA, 6-hop chain to FactTableA"

- intro: 2–4 sentences of narrative prose as a standalone paragraph before the sections. Open with the direct answer to the user's stated question — name the origin, the key relationship, or the finding the user asked for — then set architectural context. Refer to shared state by role ("central scratch-pad table", "terminal publication step") rather than by listing its columns. Schema details (column names, data types, nullability) belong in the later sections.

- closing: Required whenever this template appears — the engine renders it only for results large enough to need a wrap-up. After the sections, separated by a `---` divider, write a brief closing block: (1) one-paragraph through-line that names the overall pipeline answer in the lens the user requested. Add a risk callout block only when there is a significant, decision-impacting issue grounded in captured evidence. In business-only missions, keep callouts business-facing (impact/scope), not technical internals. If no significant issue is present, omit risk callouts. Write complete sentences and finish the closing cleanly.

- highlights: Colors and labels are two different channels, both relative to the USER QUESTION. Colors (highlight_groups) mark importance: the question's data Sources, its Target, and the important transformations — nodes that CREATE or CHANGE the answer's values (formula, condition, classification, status transition). Carry-through plumbing (renames, SELECT * bridges, movement procs, plain storage tables, row filters) stays uncolored — the graph is a map: colored landmarks on a plain background. Highlight selectively: emphasis, not the full node list; the linked sections already carry the complete set. Pick one scheme: Lineage (source/transform/target) or Diagnostic (good/warn/fail). Keep one scheme. Lineage colors follow DATA FLOW, not question direction: `source` = the deepest data origins the trace reached (raw/base feeds), `target` = where the data lands — in an upstream trace that is the queried object itself.

- notes: Per-node captions (node_id, text). ONE short sentence under each node — what it does specifically in this flow, not a generic description. Keep it terse; ~120 chars typical. No SQL snippets, no formulas, no multi-line captions. Detail belongs in the section body, not in the graph caption. Glancing at graph + notes should tell the story; deeper logic lives in the description. If the node is a passthrough, name what it passes or filters in one short clause ("Passthrough — IsValid filter"). GOOD: "Computes NetAmountA at INSERT" BAD : "Computes NetAmountA = QtyA × PriceA at INSERT\nAlso computes AdjustedAmountA" (multi-line + formula belongs in the section body).

- general: Apply this rendering set across every assembled section so the document reads consistently end-to-end. Prioritize business clarity; include technical formatting only when needed to clarify business meaning:
- **Formulas**: every calculation present in the captured bodies that
  bears on the asked question appears exactly once as a `$$ … $$`
  block in its most relevant section; ground every formula in
  captured content.
- **Column renames**: render as a `| From | To | Business meaning |`
  table only when the rename pattern is central to business understanding.
- **Source guards** (WHERE / JOIN / MERGE predicates that filter or key
  the data): quote short SQL snippets only when needed for business
  clarification; use fenced ```sql blocks with short snippets, not full
  statements.
- **Status-enum lifecycles**: express as numbered transitions
  ("1. New → 2. Approved → 3. Shipped").
- **Risks / data-quality flags**: include ⚠️ only for material,
  decision-impacting issues backed by captured evidence. In
  business-only missions, phrase risk in business terms first; add
  technical detail only when it clarifies impact.
- **Scope**: answer ONLY what was asked. Side branches the question did
  not ask about (audit, logging, retention, error-handling paths) get at
  most a one-line note, not their own section or highlight. In a
  column trace, sections and highlights follow the value chain of the
  traced column and its terminal sources.

These rules apply only when the captured body has the underlying material. Use sourced tables, formulas, and fences only.

- loading_pattern: Technical-angle closing addition. When all bodied procedures in scope share a single load shape, name it once — in `closing` if a closing is requested, otherwise in the section that covers the load — because the pattern is one statement about the whole pipeline, not per section. Recognized shapes (coarse — no SCD1/SCD2/CDC sub-variants):
- `reload`        TRUNCATE + INSERT / full refresh - `append`        INSERT-only, no UPDATE or DELETE - `upsert`        MERGE or UPDATE + conditional INSERT - `historization` versioned history / change tracking - `purge`         DELETE-only / retention - `orchestration` EXECs other SPs, no data mutation on the target
Skip when shapes differ across procedures, when the analysis spans non-bodied origins only, or when classification is `business`.
