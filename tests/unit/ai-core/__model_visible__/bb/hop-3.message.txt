When writing `sections`, use `{"business": …, "technical": …}` — classification=both keeps both keys, one key per angle, and cover the applicable capture instructions across those string values. Markdown without headings. Back each grain predicate, formula and any evidence-supported ⚠️ line with one short ```sql fence of its deciding expression, an exact substring of `ddl`; what the SQL does not establish reads `not established from the available SQL`. Skip an item the SQL lacks.

Record shared facts, formulas and deciding SQL once across the two section strings. Use business as the primary explanation of the facts, meaning and consequences, and technical only for additional implementation detail; do not write two complete walkthroughs.

Formatting instructions describe the decoded section string. In tool-call JSON, encode its line breaks, double quotes and backslashes as JSON string escapes so the SQL and LaTeX decode unchanged; keep structural JSON quotes unescaped and omit trailing commas.

The recipe items are a coverage checklist, not disconnected output fragments. Write each substantive calculation, and each intermediate result another calculation builds on, once within its natural rule or transformation step: explain the inputs and affected rows, show the formula, explain its defined meaning and consequences, and quote the deciding SQL there. Across the combined capture, use a LaTeX `$$ … $$` block on its own lines, or a LaTeX `$ … $` formula in a table with a short description of its meaning; short formulas may also sit inline within their explanatory sentence. Arithmetic, aggregate and window expressions in the supplied SQL define calculations; they do not establish observed statistics, counts, elapsed time or performance. Describe a calculated value only when its defining expression is supplied; report a measured result only when matching data or runtime evidence is supplied. These math delimiters are required. A formula carries every term and branch of the SQL it restates. Do not create a separate Formulas subsection. Capture this complete explanation in detail memory; a list of calculation names is not their explanation. Simple renames need no equation. Keep SQL quotes contiguous and verbatim: omit unrelated SQL by choosing a shorter quote, never by inserting ellipses. Describe intermediate and final surviving grain separately; later deletion or validation can leave zero rows from an earlier partition.

- Shared capture coverage. Put all analysis in `sections`; text outside the tool call is discarded. Put every applicable item:
1. Purpose: the node's role in the data flow.
2. Rules and branches: each declared value of a mode, status or strategy switch and what it changes; a commented-out branch is declared, not active.
3. Grain: distinguish input rows from surviving rows at each cardinality-changing step. For grouping or ranked-row removal, derive survivors per grouping or partition key from retained count or rank. Quote the deciding SQL.
4. Column mapping: `| From | To | Business meaning |`.
5. Steps: a numbered walk of statements, calculations and status transitions in order; naming a computation without explaining it leaves the section incomplete.
6. Loading: whether target rows are replaced, extended or removed.
7. Error handling: what a failure leaves in the rows.
8. Gaps: material unresolved evidence.

- business: Domain impact on data meaning.
Explain the domain role, supported decisions, and business definitions and consequences of calculations. For conditional eligibility, evaluate complete predicates with defaults and overrides separately.

- Consider question-relevant SQL comments, verify their claims against SQL and metadata, and flag contradictions in a callout. Other ⚠️ findings are optional: use them only when the supplied SQL proves specific row or value loss, duplication or overwrite, or supplied schema or business evidence proves a violated requirement. Quote the deciding expression and any evidence of the requirement. For a no-transaction failure window, require at least two ordered writes to persistent data: the first changes persistent state and a later persistent write is needed to complete the same operation. Temporary objects, variables, reads, calculations, and steps before a single persistent write do not create that failure window. State filters, literals, defaults, join hints, grouping and row grain as SQL facts unless supplied evidence proves an adverse effect. Claims about index presence or use, actual seeks or scans, statistics, estimated or observed row counts, execution plans, chosen physical join strategies or runtime costs require matching catalog, plan or runtime evidence; SQL hints alone do not establish what the engine executed or its performance. Do not create a callout merely because evidence for a requested dimension is unavailable; state its absence once in factual prose.
